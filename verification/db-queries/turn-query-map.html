Why one agent turn talks to the database so much

Measured on 2026-10-22 — a real customer turn on tkb-demo (2 add-ons: a field extractor and the Talker), local server.

The turn is not doing anything wrong — every query has a reason. But it was written step by step, each step reading what it needs for itself. So the same things are read several times (the conversation 3×, the history once per add-on, the memory before every save), and the agent's setup takes 4 separate reads. None of that is needed for the answer the customer gets.

Why so many — the pattern

  • Each step reads for itself. The chat route, the "which crew" check and the runner each read the same conversation row — 3 reads where 1 does.
  • The agent's setup is four questions, not one. Agent → its version → crew → its version, one after another.
  • Every add-on fetches its own history, even when two add-ons want the same last messages.
  • Every memory save reads before it writes — a shared helper from the older platform (contextService.saveContext) that asks "does a row exist?" before updating, although the runner just loaded it.
  • Small writes wait in line. The add-on trail is written while the next add-on waits for it.

None of these affect what the customer gets. They were the simplest way to write each step on its own.

Where the time goes

Most queries run one after another, so each one's travel time adds to the turn. Locally every trip is about 65 ms (Israel → the database in Belgium), so it shows up plainly:

A local customer turn, 5.5 s
DB 0.8 s extractor model 2.1 s Talker model 2.2 s
Orange = waiting for the database (about 20 trips in a row ≈ 1.3 s, 25% of the turn). Blue = the models.
In production this is much smaller. The servers sit next to the database, so a trip is a few milliseconds: the same 20 trips cost roughly 40–60 ms of a 5 s turn. The customer will hardly feel the cut. What production gains is capacity: half the queries means each turn holds a database connection half as long, so the same pool (and the database's limit of 50 connections) serves about twice as many people at once.

6Lighter simulated turns — don't read the whole conversation back after every simulated turn when the job only needs the add-on statuses~6–8 (simulations only)LowCustomers are untouched; only the simulation layer.
7Write the trail and the usage log without waiting, all at the end of the turn in one go2 per add-on → 2 per turnMediumThe chat shows the trail live from events (unchanged), but a reload right after a turn must still find it; a crash mid-turn must not lose it.

Steps 1–4 are small and contained (≈ 7 queries off every turn). Step 5 and 7 are where care is needed.

Doing it safely

  1. The map is the test. The measuring tool used here stays in the repo: before and after each step, one real turn, and the query list must shrink exactly as planned — nothing else changes.
  2. Same turn, same result. The same scripted conversation before and after: same replies' context, same memory after every turn, same add-on trail. Compared automatically.
  3. The existing batteries (simulation jobs, error center, load tests, MCP) after every step.
  4. Then a load test on production — 1, 5, 10 at once — to see the real effect on time and on the database pool, which a local server cannot show.
  5. One step per change, each one shippable on its own, in the order above.

How this was measured

A local server started through a small wrapper around the database driver (no code change): every query recorded with its start time, how long it took, and its SQL. A customer conversation on tkb-demo (the outside chat, the active version) ran three turns; turn 2 is shown above, turns 1 and 3 match it (23 and 24 queries; turn 1 includes naming the conversation). Two background queries of the trigger clock that happened to fall inside the turn are left out. The code location of each query was traced by hand from its SQL — the driver hides the call site.

Numbers for other agents are calculated from the pattern. Production timings are estimates; the 65 ms per trip is measured from this machine.
