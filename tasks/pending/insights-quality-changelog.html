Making the reports true

Reports were stating numbers that were confidently, badly wrong — some by 127×. The cause was not bad SQL. This is what was wrong, what changed, and what is measurably better.

What was actually wrong

The write-up model saw 30 rows of a 20,723-row result and treated them as the whole business.

Every total, ranking and percentage was computed over 0.14% of the data. The independent fact-checking pass confirmed them all — correctly, on its own terms, because those numbers really were present in the rows it was shown. It was checking whether figures came from the data, not whether the sample represented it.

The fixes that matter

Aggregates computed in code, never by the modelcore

The full result set is now re-aggregated in plain JavaScript back to the grain the question actually asked for — grand totals, true per-entity ranking, pre-computed shares, exact extremes. The raw rows are demoted to an illustrative sample the model is forbidden to sum.

It works even when the SQL is wrong: a later run still returned the 20,723-row grain, and the digest collapsed it to 28 campaigns with every number correct.

Impossible results are rejectedcore

A filtered query can never total more than its own fact table, so anything larger has duplicated rows through a join. Caught a query reporting ₪362.9B for a florist chain whose entire sales table totals ₪51M — 6,379× over the ceiling.

This is the only guard that can catch a query which is itself wrong; every other check validates a figure against that same wrong query.

A silent 44.6% inflation on every product figuredata

The product lookup holds 62,163 rows for 55,189 distinct keys, so joining it before totalling multiplied every measure. No error, no warning, entirely plausible numbers — just 44.6% too high.

Nine tables that do not existdata

One dataset's hand-written rules — the highest-authority instructions the system follows — named nine materialized views that had been deleted. Every store, revenue and target question for that client failed or returned nothing, for months, because nothing ever checked.

A contract test now fails the build if any named table or column is missing. Rules were rewritten against the live schema.

The same question gave different answerscore

SQL generation ran at the provider's default randomness, so asking the same thing twice produced different queries at different grains — and therefore different numbers. Now pinned deterministic.

"Last 4 weeks" of nothingdata

These datasets are periodic exports, not live feeds — one was 106 days behind. Every recent-window question anchored to today was correctly empty. Windows now anchor to the date the data really ends.

Confidence now means somethingcore

The score was whatever the model felt like reporting. It is now the lower of what the model claimed and what the evidence supports — row count, query confidence, verification verdict, data-quality flags — with every deduction shown to the reader.

What users see

  • Progress that tells the truth. The bar animated against a hardcoded 8 seconds while real runs take 30–100s, so it hit 96% in under 8 seconds and froze. It now follows the real pipeline stage, and the time estimate comes from the same model as the percentage, so the two cannot disagree.
  • The original question is shown above the rewritten headline — previously there was no way to tell from a report what it was answering.
  • Suggested reports actually appear. They were being generated under a system account that no user's view could ever read. Now shared across sessions, refreshed nightly, and saving one makes a personal copy.
  • Deleting asks first, quoting the report by name.
  • Answers come back in the language they were asked in — Hebrew, English, or a mix of both.
  • Suggestion cards carry a chart, with the form chosen from the data: a line for time, bars for a ranking.

How it is verified now

Four harnesses ship with this work. The important one runs real investigations, then independently re-executes each report's own SQL and compares every figure on screen against freshly computed aggregates — so "is this true?" is a command, not an opinion.

Results live in verification/<topic>/, each with a short README recording what was checked, how to reproduce it, and a summary table. Raw JSON is gitignored as regenerable output.

Known limits — deliberately written down

Statistical significance is still untestedopen

A −219pp margin swing on ₪119 of sales is arithmetically correct and analytically worthless. Extremes now carry their base and a materiality filter exists, but it informs the write-up rather than forbidding it — and one such finding is currently visible on the reports page.

Eight of 42 questions still failopen

Mostly inventory and sell-through questions across three unrelated datasets — a clustering that suggests one shared cause worth chasing, not eight separate ones. One "failure" is the impossible-result guard doing its job.

Causal and forward-looking claims are unverified by designby design

"Why did margin drop" cannot be settled by one aggregate query, and scenario projections are explicitly exempt from fact-checking. Both are plausible, not derived.

The architectural fix has not been donenext

A semantic layer already exists elsewhere in the codebase, where joins, record types and non-summable measures are correct by construction and an unknown field returns an error rather than a plausible wrong answer. Routing investigations through it would make an entire category of defect impossible instead of merely detected.
