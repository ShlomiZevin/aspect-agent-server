Getting the report pipeline to tell the truth

A measured baseline across all six datasets, the diagnosis it points to, and a sequenced plan. The headline finding: verification now works — the remaining failures are wrong queries, not wrong write-ups, and no amount of downstream checking fixes those.

Where we actually are

42 real investigations — 3 system-proposed prompts plus 4 hand-written cases per dataset. Every figure re-checked by re-executing the insight's own SQL.

What the evidence says

Verification checks whether a number came from the data. It cannot check whether the query asked the right question.

The work already shipped moved the failure mode. Write-ups no longer misread correct data — the code-computed aggregates fixed that, verified exactly against the client's own Qlik dashboard. What remains is queries that were wrong from the start, and those produce confident, plausible, entirely fictional numbers.

The plan

Sequenced by dependency, not by preference. Each horizon makes the next one measurable.

H0

Stop the bleeding

days · low risk
Raise the statement timeout for insights8 failures

The 15-second limit is a chat constraint — a user waiting on a reply. An investigation is asynchronous background work already taking 30–100 seconds; there is no reason it inherits that budget.

Clears the 8 timeout failures outright. One configuration value.

Regenerate the four stale schema descriptions≈11 failures

newdeli, thestock, tevanaot and zolstock are running on descriptions generated one to three months ago. They also pre-date the duplicate-key detection, so they pick that up for free.

zolstock has 34.7M sales rows and real revenue columns, yet returned zero rows on 5 of 7 cases — that gap is stale schema knowledge, not missing data.

Deduplicate the product join in the BI semantic layersilent 45% inflation

The NL→SQL path is fixed. bi/datasets/hypertoy.dataset.js still joins f.part = p.part raw, so any product-dimension query through Aspect BI inflates the same way.

products holds 62,163 rows for 55,189 distinct parts. One line, one place, permanent.

H1

Make vendor knowledge provable

1–2 weeks
Turn rule validation into a failing test9 fictional tables

Per-dataset rules are necessary — record types under Hebrew labels, reversed payment names, and numeric campaign codes are not inferable from column types. The problem is that nothing proves them true. A runtime corrector now patches around bad rules; a test makes them get fixed instead.

The zer4u rules name 9 materialized views that do not exist, presented to the model as "CRITICAL — follow exactly". Undetected for months.

Split structural facts from methodologydesign

Two kinds of knowledge are tangled in one 1,200-line string. Structural claims — which table, which join, which measure — are checkable against the live catalog and belong in a declarative form. Methodology — use a Z-score for anomalies, pace-adjust a partial month — cannot be machine-checked and is genuinely good prose that should stay prose.

The zer4u rules are roughly 90% structural, which is precisely why they rotted invisibly.

Move editable knowledge into the admin UIplumbing exists

Per-dataset config already supports version history, restore and non-developer editing. Only the plain-language data model uses it today; vendor rules still require a developer editing source.

Rewrite the zer4u rules against its real schemadataset broken

Contained, measurable work with a known before state: 4 of 7 cases, two hard failures, and a ₪362.9B headline.

H2

Make wrong queries impossible

weeks · highest leverage
Route investigations through the semantic layerstructural

Aspect BI already compiles a structured spec into SQL: record types handled by construction, joins declared once, and margin defined as a ratio of two sums so it cannot be summed. An unknown field returns an error rather than a plausible wrong answer.

The planning step already emits measures and dimensions — that is most of a spec. The work is extending the five missing dataset definitions and keeping NL→SQL as the fallback for questions a spec cannot express.

Eliminates by construction: missing record-type filters, phantom tables, summed percentages, unexpected grain, and run-to-run drift.

Measure baselines per datasetcatches ₪362.9B

Store each core measure's fact-table total, refreshed on data reload. Any reported figure exceeding it is impossible and gets rejected before a user sees it. Cheap, deterministic, and the check that kills the cartesian-join class.

Control-total invariantfollows H2

For any aggregate over a join, compare against the same measure on the fact table alone. If the joined total is larger, the join fans out. Hard to extract from free-form SQL; nearly free once a compiler knows the base table and filters.

H3

Make quality visible and non-regressing

ongoing
Golden-answer regression suite on a scheduleharness built

The runner exists and already re-verifies every displayed figure against re-queried data. What it needs is known-answer questions per dataset and a schedule. The client's own Qlik dashboard is the ideal seed: total sales, revenue by branch and by product family all reconcile to the shekel today.

Raise the share of figures that are checkablemeasurement gap

Only 74 of 214 displayed figures could be automatically verified; the rest are percentages, projections or derived ratios with no direct counterpart. That share is itself a quality metric — the more of a report that is mechanically checkable, the less rests on trust.

A second query for significanceanalytical

Let the planner emit a baseline query — prior period, or the population average — alongside the finding. This is what turns "X is lowest" into "X is lowest, and that is N deviations from its own history", which is the difference between a ranking and an insight.

What this plan will not fix

  • Causal claims. "Why did margin drop" cannot be established by one aggregate query. The write-up will still narrate cause over a descriptive result, and no verification step checks causation.
  • Forward-looking scenarios. The good / neutral / negative projections are explicitly exempt from fact-checking. They are plausible, not derived.
  • Semantic plausibility without a baseline. Nothing knows a florist chain cannot bill ₪362.9B until measure baselines exist — that is why H2 matters more than another prompt rule.
  • Business judgment. A materially correct finding can still be the wrong thing to look at. That is a product question, not a pipeline one.

Recommended order

Start with H0. It is hours of work, carries almost no risk, and plausibly converts a large share of the 21 failed cases into working reports — which also gives H2 a clean baseline to be measured against. Run the suite before and after so the change is a number, not an impression.

H1 next, because it stops the same class of rot recurring while H2 is being built. H2 is the real fix and the only one that makes an entire category of defect structurally impossible.
